Evidence-backed questionnaire verification

Survey QA

Survey QA reads the Word questionnaire that defines your survey, turns it into a fixed list of requirements, and then drives a real browser through the programmed survey until every requirement has been checked or explicitly accounted for. The document is the source of truth: where the live survey disagrees with it, that is a problem in the survey, and where the document itself is unclear, we say so instead of guessing. Every result is tied to something we recorded, and anything we did not test is reported as not tested — never as passed.

What works today: all six steps below run for real. Your questionnaire is read by two independent passes, the requirement list is fixed and fingerprinted before any browser starts, checks are planned against it, a real browser drives your survey, verdicts are worked out from the recorded evidence, and the report is built from that record. A submitted run does real work and spends real money up to the cap shown below.

What is not settled yet: a result has to name which build of the survey it is about, and no such name is configured here, so every report is marked “no current results” and should be read as evidence rather than as a pass. Separately, no real survey has yet been walked end to end from inside this service — the one completed live run was pointed at a placeholder URL and stopped, correctly, with a named reason. A run can also stop early because the requirement list refused to freeze, or because a limit was reached; a run that stopped early still produces a report that says so.

The six steps

How a run works

Each step below says what it does and how far it has been proven, because a description of what something does is not evidence that it did it. All six are implemented and have run on the deployed service; the one that has not yet been proven against a real survey says so on its own card.

Step 1 · Reading questionnaire
Built

The questionnaire is read into a list of requirements, each tied to the passage it came from. The list is fixed and fingerprinted before any browser starts, so a run can never quietly rewrite its own total.

Step 2 · Preparing checks
Built

Checks are planned that cover every requirement on the list, plus extra exploring on top. Exploring can only add findings; it can never change the total.

Step 3 · Testing survey
Built · not yet proven on a real survey

A real browser walks the routes a respondent would take and records what it saw, with evidence. A real browser catches what a simulated one cannot — including a survey that does not open at all. This step is implemented and has acquired and driven real browser sessions on the deployed service, but the only run to reach it was pointed at a placeholder URL, so it stopped with walks blocked by site — the correct answer for a page that is not a survey. No real survey has been walked end to end here yet.

Step 4 · Reviewing evidence
Built

Results are worked out from the recorded evidence rather than written by whatever made the claim. A claim its own evidence contradicts does not become a pass.

Step 5 · Resolving findings
Built

Disagreements are settled with the disagreement kept on the record. Anything still unclear is held back from pass/fail and shown as unresolved rather than decided by majority. The engine that does this now runs inside the service, as part of every run.

Step 6 · Preparing report
Built

The requirement list becomes the report: every requirement visible, every result an explicit state, the two totals reported separately, and a finished report is allowed to describe testing that stopped early.

Method

What a run does not prove

Saying what we cannot show is part of the product. A run shows that the requirements on the list were checked or explicitly accounted for, and that every result shown is tied to something we recorded. It does not show that we read your document perfectly, that every route a respondent could take reached the list, or that a requirement we never tested is fine.

  • Checked is not passed. Whether we tested something and whether it was correct are two different answers with two different labels, everywhere, always.
  • Not tested is not a pass. Never reached, blocked, stopped at the cost limit, stopped at the time limit, not completed, and could not be tested in the browser each appear as themselves.
  • Two totals are never added. Requirements from your questionnaire and the individual checks that cover them count different things and are reported separately.
  • A claim is not a result. The result is worked out from the recorded evidence; whatever made the claim never writes its own verdict.
  • Unclear stays unclear. A requirement your document does not settle is held back from pass/fail and says so.
  • A signature is not correctness. Whether the records are intact, whether the evidence files still match, whether a person reviewed the requirement list, and whether the results were re-checked are four separate statements — and none of them says your survey is fine.
